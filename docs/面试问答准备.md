# 面试问答准备 — 个人知识库 AI 问答服务

> 对照 PRD 第十二节六个问题，每题按"设计思路 → 权衡 → 踩坑/扩展"结构展开。

---

## Q1. 为什么用异步队列处理文档，而不是同步处理？

### 设计思路

文档上传后需要经过三步重型操作：文本提取（pypdf 解析 PDF）→ 分块（500 字 + 100 字重叠窗口）→ embedding 向量化（本地 bge-small-zh 模型推理）。对一个 5MB 的 PDF，这三步合计可能需要 10–30 秒。如果在 HTTP 请求内同步执行，接口会超时（客户端默认超时通常 30s 以内），且在等待期间服务线程被占满，并发能力大幅下降。

实现方案：上传接口只做两件事——保存文件内容到数据库、往 Redis 的 `documents` 队列推入任务 ID，立即返回 `{status: processing}`；RQ Worker 容器从队列取任务异步执行，处理完成后更新 `documents.status` 为 `completed` 或 `failed`，客户端轮询 `GET /documents/{id}` 查看状态。

### 权衡

- 优点：接口响应时间从 10–30s 降至 <100ms；worker 失败可重试（配置 `retry=3`），不影响主服务；worker 可水平扩展（多个 worker 并发消费队列）。
- 代价：引入了"最终一致性"——上传后立刻提问，如果 worker 还没处理完，向量库里没有该文档的 chunk，回答会说"资料中没有找到相关内容"。这是可接受的权衡，前端可提示"文档处理中，请稍后提问"。

### 扩展

任务框架选 RQ（Redis Queue）而非 Celery，原因是 MVP 阶段 RQ 配置更简单（只需 broker URL），代码量少；若后续需要定时任务、任务链、Canvas 等高级特性，可迁移至 Celery。消息队列本身若需要持久化保障（避免 Redis 重启丢任务），可切换至 RabbitMQ 或 Kafka。

## Q2. 向量检索的 Top-K 如何选择？检索不到相关内容时如何处理？

### 设计思路

Top-K 默认值设为 4（`config.py: top_k=4`，可通过 `.env` 覆盖）。选 4 的考量：检索结果拼成 Prompt，太少则上下文不足，太多则 token 消耗增加且可能引入无关 chunk 干扰模型判断。4 个 chunk × 500 字/chunk = 约 2000 字上下文，对 Claude 1M 上下文窗口而言很宽松，同时 prompt 成本可控。

检索实现：`retrieve_chunks` 联 `Document` 表过滤 `user_id`，对问题向量化后用 pgvector 余弦距离排序取 Top-K。

检索为空的处理路径在 `generate_answer` 函数中：`if not chunks: return NO_RESULT_ANSWER`，直接返回固定提示语"知识库中没有找到相关内容，请先上传相关文档或换个问法"，不调用 Claude API（节省费用），也不报错。

检索到 chunk 但语义不相关（余弦相似度低）的处理：在 system prompt 中要求模型"若资料片段不足以回答，必须明确回答：资料中没有找到相关内容，不允许编造"，由模型判断是否有依据回答，避免幻觉。

### 权衡

固定 K 值的缺点是无法动态感知相关性——相似度极低的 chunk 也会被拼入 prompt。更精确的方案是设置相似度阈值（如余弦距离 < 0.3 才纳入），但 pgvector 的余弦距离值受向量空间分布影响，阈值需要根据实际语料调参，MVP 阶段用固定 K 更稳定可控。

### 扩展

生产环境可结合 Reranker（如 bge-reranker）对 Top-K 结果二次精排，提升 precision；也可实现"相似度阈值过滤"，只取距离小于阈值的 chunk，解决检索到无关内容的问题。

## Q3. 缓存 key 如何设计？缓存失效策略是什么？如何避免脏数据？

### 设计思路

缓存 key 格式：`qa:cache:{user_id}:<sha256(normalize(question))>`

- `user_id` 维度：确保用户只命中自己问题生成的缓存（详见踩坑）。
- `normalize`：`question.strip().lower()`，对问题做归一化（去首尾空格、统一小写），避免"什么是RAG" 和 "什么是rag " 因格式差异造成缓存穿透。
- `sha256`：question 可能很长，hash 后 key 固定 64 字节，节省 Redis 内存，也避免特殊字符问题。

失效策略：TTL 固定 1 小时（`cache_ttl_seconds=3600`）。1 小时后缓存自动过期，下次提问重新调用 Claude。不做主动失效（文档更新时不清除旧缓存），因为 MVP 场景下文档删除后用户下次提问重新检索，自然得到新答案；1 小时 TTL 足够短，可接受短暂的陈旧缓存。

避免脏数据：删除文档时，对应 chunks 从 pgvector 中级联删除，下次提问（缓存过期后）检索不到已删除文档的内容，答案自动更新。若需要立即一致，可在 `DELETE /documents/{id}` 接口中主动 `redis.delete(cache_key(...))`，但需要知道该用户缓存了哪些 key（可用 key 扫描或维护 key 集合），MVP 阶段用 TTL 过期即可。

### 踩坑：跨用户缓存泄漏

初始版本缓存 key 未包含 `user_id`，格式为 `qa:cache:<sha256(question)>`。冒烟测试时发现：用户 B 提同一个问题，命中了用户 A 的缓存，返回了基于用户 A 文档内容生成的回答——这是严重的多租户数据泄漏。

修复：缓存 key 加入 `user_id`；`retrieve_chunks` 联 `Document` 表过滤 `user_id`。这个"发现→修复"过程本身说明冒烟测试的必要性：纯单元测试 mock 掉了用户隔离的场景，只有真实端到端才能暴露。

### 扩展

可在用户级缓存之上加全局语义缓存层（对 question embedding 做近似匹配），使语义相近的问题也能命中缓存，进一步减少 Claude 调用；但需确保缓存内容不含用户私有信息，需做脱敏审计。

## Q4. 限流算法选择的原因（令牌桶 vs 固定窗口 vs 滑动窗口的权衡）？

### 设计思路

选择固定窗口算法，实现仅需两条 Redis 命令：

```python
window = int(time.time()) // 60      # 当前分钟窗口 ID
key = f"rl:{user_id}:{window}"
count = redis.incr(key)              # 原子自增
if count == 1:
    redis.expire(key, 60)            # 首次写入时设 TTL
if count > RATE_LIMIT:
    raise HTTPException(429, "Rate limit exceeded")
```

代码极简，无 Lua 脚本，无额外数据结构，延迟 <1ms。

### 权衡

三种算法对比：

| 算法 | 实现复杂度 | 突刺容忍 | 适用场景 |
|---|---|---|---|
| 固定窗口 | 低（2条Redis命令） | 窗口边界可突发 2N | 个人工具、内部服务 |
| 滑动窗口 | 中（sorted set + 时间戳） | 无突刺，平滑 | 付费 API、精确计量 |
| 令牌桶 | 高（Lua脚本原子操作） | 允许短时突发 | 需要弹性突发的场景 |

固定窗口的核心缺点：窗口边界处可在前 1 秒发 N 次、后 1 秒再发 N 次，实际 2 秒内消耗 2N 次配额。对本项目（限制 Claude 调用成本，默认 10 次/分钟），这个突刺造成最多 20 次/2 秒，可接受。

### 扩展

若接入商业化场景（按调用计费的 API 网关），应换用滑动窗口（精确）或令牌桶（支持突发）。滑动窗口用 Redis sorted set 实现：key 为 `rl:{user_id}`，每次请求 `ZADD` 当前时间戳，`ZREMRANGEBYSCORE` 清除窗口外记录，`ZCARD` 计数。原子性靠 Lua 脚本保证。

## Q5. 如果这个系统要支撑更大并发，你会如何扩展？

### 设计思路

当前架构单点如下：单台 FastAPI 容器、单 PostgreSQL（pgvector）、单 Redis、单 RQ Worker。MVP 场景够用，但并发上来后各层都需要扩展。

**接入层**：FastAPI 无状态，可直接水平扩展多容器，前置 Nginx 或云负载均衡。

**数据库层**：
- 读写分离：query_logs 写主库，历史记录查询走只读副本。
- 连接池：当前用 SQLAlchemy 默认连接池（pool_size=5），高并发下需调大或引入 PgBouncer 连接池代理。
- 向量库独立部署：chunk 数量达到百万级时，pgvector 的线性扫描（无 HNSW 索引）性能下降，可迁移至 Qdrant/Milvus，与 PG 解耦。
- 分表：query_logs 按 user_id 哈希分表；documents/chunks 按 user_id 分库（多租户场景）。

**缓存层**：Redis 单实例扩展为 Redis Cluster（分片）或 Redis Sentinel（高可用）。问答缓存命中率提升后可缓解大量 Claude 调用压力。

**异步任务**：RQ Worker 水平扩展多实例（共用同一 Redis broker），文档处理并发能力线性提升；重型任务（大 PDF）可用优先级队列（RQ 支持多 queue）隔离，避免阻塞小文件。

**大模型调用**：Claude API 有速率限制，可实现请求队列 + 指数退避重试；或接入多个账号/区域轮询。

### 权衡

扩展优先级应按瓶颈实测而定——先上监控（Prometheus + Grafana），找慢查询和热点，再针对性扩展，避免过度设计。

## Q6. 大模型调用失败/超时时，系统如何降级，不影响整体可用性？

### 设计思路

`rag.py` 的 `generate_answer` 函数对 Claude SDK 异常做分级处理：

```python
except anthropic.RateLimitError:
    # 429：Claude 自身限流，读 retry-after header
    raise HTTPException(503, "AI 服务繁忙，请稍后再试")

except anthropic.APIStatusError as e:
    # 5xx：Claude 服务端错误，SDK 已自动重试 2 次
    raise HTTPException(502, "AI 服务暂时不可用")

except anthropic.APIConnectionError:
    # 网络不通（DNS/TCP 失败）
    raise HTTPException(502, "AI 服务网络异常")
```

所有失败路径均返回结构化 JSON 错误，HTTP 状态码语义明确（429/502/503），前端可据此展示用户友好提示，而不是崩溃或返回空白。

检索为空时（`chunks` 为空列表）不调用 Claude，直接返回固定提示语——这是另一条"降级"路径，彻底避免无意义的 API 调用。

### 踩坑：health 接口的 DI 陷阱

`/health` 接口若通过 FastAPI 的 `Depends(get_db)` 注入数据库 session，当 PostgreSQL 完全不可达时，依赖注入阶段（在进入 handler 函数之前）就会抛出连接异常，FastAPI 将其转为 500，而不是进入我们的 try/except 返回 `degraded`。

修复：`health.py` 直接使用 `engine.connect()`（绕过依赖注入），将 PG 连接放在 try/except 守卫内，确保任何情况下都能返回 `{"status": "degraded", "postgres": false, "redis": true}` 而非 500。这满足了"依赖不健康时 /health 仍返回 200 + degraded"的运维要求。

### 踩坑：get_db 不提交陷阱

SQLAlchemy session 默认 `autocommit=False`，若 `get_db()` 只 `yield db` 而不 `commit()`，所有写操作（`db.add(QueryLog(...))` 等）只存在于本地 session，进程退出后丢失。

修复：`get_db()` 改为 commit-on-success 模式：

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
        db.commit()   # 成功时提交
    except Exception:
        db.rollback()
        raise
    finally:
        db.close()
```

### 扩展

生产环境大模型降级可做得更精细：
- 熔断器（Circuit Breaker）：连续失败 N 次后自动熔断，避免雪崩；冷却期后半开探测。
- 回退策略：Claude 不可用时回退到本地规则引擎（如直接返回 Top-1 chunk 内容），保留基础可用性。
- 异步降级：将失败的问答请求入队，Claude 恢复后异步补答并通过 webhook/轮询通知用户。
